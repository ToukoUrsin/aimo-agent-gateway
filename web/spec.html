Junction 2026 prototype on Valio Aimo's challenge data and mock API. Not a Valio Aimo system.

How it works

This page is for Valio Aimo's IT. The shop chat on /shop is the gateway's first user, and there nothing is ordered before the person in the shop confirms. The same gateway can let a customer's own software look up products, get a fixed price and place an order inside limits both companies set, once Valio Aimo opens that for the customer. Anything outside the limits goes to a person as one link.

The gateway sits in front of Valio Aimo's price and availability API. The rules run in code, never in a model. Every price, every decision and every order is signed, so either side can prove later what was agreed.

The first caller is Valio Aimo's own: a chat in its web shop (/shop), where the signed-in cook or purchasing manager says what they need and the order is built, and a menu photo (/menu). A customer's own purchasing software, or a chat assistant, comes through the same door under the same rules. /access shows what any of them can see for one account.

Three things go further than a safe door. A menu photo becomes one checked order. Valio Aimo has its own agent at the door, so the customer relationship stays with Valio Aimo whatever assistant the kitchen uses. And short stock is split by contract share when every agent asks at once.

One order, step by step

  1. The buyer gives its agent a mandate. A signed file that says what the agent may do alone: how much per order and per week, which products, which substitutes.
  2. The agent asks what is possible. "1,000 litres of lactose-free milk by Monday." The gateway answers with ready options at the customer's own price and live availability, and says for each whether the agent may order it alone.
  3. The agent picks one and gets a signed offer. Price and stock are held for 20 minutes. The offer lists every rule that was checked and how it came out.
  4. If a rule says so, a person decides. The buyer's approver gets a link, sees the order and why the agent is asking, and approves or rejects. Once the account has enrolled an approver's phone or laptop, the yes is signed inside that device with its fingerprint, face or screen lock, and the link alone no longer approves.
  5. The agent signs the offer and the order is placed. Valio Aimo signs the confirmation. The order also comes out as a Peppol order, so it can go into the same flow as any EDI order.

Connect your own agent

Nothing here is tied to one model or vendor. Which software may connect, and for which customer, is Valio Aimo's choice on /access.

There are two kinds of agent. One has its own signing key, named in its mandate, and signs every order with it. Prices and stock are asked per request, per customer


Prices and availability depend on the customer, so the gateway never copies the whole range. It asks Valio Aimo's price and availability API only for the products an agent's request has narrowed down to, under the customer number in that agent's mandate. Without a mandate it asks nothing; the public catalogue facts come from the catalogue.


How many products one request asks about, at most:


    

  • Search: the page of results, up to 25.
    • 

  • Lookup: 25 ids.
    • 

  • Substitutes for one product: the product and up to 120 candidates.
    • 

  • Sourcing plan: up to 200 of the kind asked for; the answer says when there were more.
    • 

  • Checkout, menu, shop chat, after delivery: their own lines and the replacements for them.
    • 



These are products per request, not requests: one request to the API carries the whole list. Measured on 15 Nov 2026 with the shop's own wedding example (five dishes, 180 guests, 26 lines in the cart): 3 availability requests and 3 price requests in all, from the message to the finished cart.


An answer is kept for 45 seconds per product, delivery day and customer, so an agent that asks again at once is answered from that. A list longer than 1,000 products goes out in pieces of 1,000, the API's own limit. When the API says it is busy or fails, the gateway tries again at once, then after 0.6, 1.8 and 4 seconds; if it still fails, it answers from the last kept answer and marks it as old. An agent that has never ordered and looks up 40 different products within 10 minutes is refused (rule W4).


Three things ask on their own, not for one agent's request:


    

  • Valio Aimo's own agent runs every 30 minutes (the first run within 90 seconds of a start). For each demo account it watches, now one, it asks for that account's usual products and the lots it is following.
    • 

  • The warehouse view on /tower asks once after a restart for up to 25 held products not already kept, under the customer number "public".
    • 

  • The Monday rush demo, when someone starts it, asks for the whole category of the product being rushed (91 products) and 3 more, under one rush customer's number, and gives that one answer to all 60 rush accounts. The challenge's mock API answers the same for every customer number (two numbers checked, same prices and availability), so the demo saves 59 identical calls. Against the real API this shortcut has to go, and each account be asked under its own number.

The mandate


A JWT signed by the buying company with the key it registered when it became a customer. It names the agent, carries the agent's own public key, and states the limits. The agent proves it holds that key every time it orders, so a copied mandate is useless.

 "iss": "https://buyer.example/nordic-harbour-hotels",   who gives the authority
 "sub": "agent:nordic-harbour/purchasing-1",            the agent
 "aud": "…/.well-known/ucp",                            only valid at this seller
 "exp": 1795210887, "jti": "mnd_531a4bfdf0b6",
 "cnf": { "jwk": { …the agent's public key… } },
 "mandate": {
  "budget": { "currency": "EUR", "max_per_order": 150000, "max_per_week": 600000 },
  "categories": ["*"],
  "exclude_allergens": [],
  "undeclared_allergens": "ask",
  "substitution": { "allow": "listed", "max_unit_price_increase_pct": 10 },
  "new_products": "ask",
  "quantity_anomaly_factor": 3,
  "after_order": { "accept_delay_days": 1, "accept_partial_min_pct": 70 },
  "approver": { "name": "F&B manager", "channel": "link" }
 }
}


undeclared_allergens says what happens when something is excluded and a product's manufacturer declared nothing about allergens: ask (the default) sends the line to a person, allow lets the agent order it and the record says the mandate allowed it.


Amounts are in cents, ex VAT. The buyer can replace or withdraw a mandate at any time. Valio Aimo has its own switch per customer on top: agent ordering on or off (off refuses every order; lookups still answer), look up only, re-order only or free ordering, its own cap per order and its own ceiling per delivery day.


The buyer's own key. A buying company registers the public half of a key it made itself: POST /api/buyer/key {"jwk": …}. The answer names the issuer, the audience and the agent prefix to write into a mandate. From then on the company signs its agents' mandates on its own side, and the gateway reads them strictly: the agent must be one of that company's own, every limit must be a number, and a field of the wrong type is refused by name. A private key sent by mistake is refused and not stored. An order placed under such a mandate records that the buyer's own key signed it, and this server could not have made that signature. The whole round runs from any machine against this site: verify/own_key.py makes the keys, registers one, signs a mandate with a €400 limit, orders 100 L alone, sees 400 L sent to a person, sees a mandate signed with another key refused, and checks the signed order against the keys that never left it.



Sourcing options


The challenge data has 349 category numbers and no names, and one category holds milk, coffee milk and sour milk side by side. So every one of the 17,546 products has a kind: the plain words a kitchen would use for it (milk, egg, minced beef, 3,702 in all). A model wrote them once from the product names and read every kind again as a whole, which moved 903 products that did not belong, such as frozen onion cubes filed under onion (gateway/kinds.json). Matching a request against them is code. "Milk" gets milk, and coffee milk is named as another kind, not offered. "600 eggs" is counted in eggs: 7 cases of 90, not 600 boxes. "Chicken" does not say which kind, so the account's history decides, and with no history nothing is offered and the agent asks: fillet, strips or thighs. "We need some milk" gets one proposal from usual_orders, the usual product in the usual amount, for the kitchen to confirm with a yes. Valio Aimo's own product hierarchy would replace the file.


plan_sourcing does the work a buyer would do by hand. It filters on the hard requirements using the manufacturer's GS1 data, drops what cannot arrive on the day, and returns a few named options: the usual product, the lowest price, the best delivery record, a split with a substitute when stock runs short, or what can be delivered if nothing covers it all. Each option says how much of the need it covers, what it costs, how it differs from the usual product, how reliably it has been delivered, and whether the agent may order it alone. Product lookups also carry the carbon figure.



From a menu to an order


A kitchen does not think in product numbers. It has a menu, a head count and a date. /menu takes a phone photo of that menu and returns one checked order.


    

  1. A model reads, and only reads. A small Gemini model first answers one question: is this a menu? Then Gemini reads the dishes, the number of guests, the date and the dietary notes. A photo that is not a menu is refused before anything else runs.
    2. 

  2. Code works out the quantities. Portions times amount per portion plus waste, from the kitchen's recipe cards. Every ingredient is mapped to a catalogue product through the same price and stock path as any order and rounded up to pack size.
    3. 

  3. Dietary notes become rules. "Nut-free" or "lactose-free" turn into allergen exclusions and required claims, checked per line against the manufacturer's GS1 data.
    4. 

  4. A shortage is solved by what the ingredient does in the dish. Cooking cream can stand in for whipping cream in a sauce. It cannot in a whipped topping, so that line is reported instead of quietly swapped.
    5. 

  5. One signed offer. The whole basket goes through the normal rules, approval link and signatures.
    6. 



Software Valio Aimo has let in can use the same planner: plan_menu_order over MCP or POST /menu/plan. /byhand lets a person do the same basket in a bare web shop over the same catalogue and times it. Until someone finishes it, the by-hand time shown is an estimate and says so.



Valio Aimo's own agent


If the only agent in the conversation is the customer's, someone else's assistant decides what the kitchen buys. So Valio Aimo has an agent of its own at the door. It speaks in Valio Aimo's name, signs with Valio Aimo's key and makes proposals to the customer's agent. See /seller.




DriftThe standing order no longer matches what the kitchen really orders, up or down. The proposal shows the last eight weeks.


Short-datedStock close to its best-before date, at a lower price, in a quantity the kitchen uses before that date.


Cut-offThe standing order for the next delivery day is not placed yet and the cut-off is close: the same lines, ready to order before it passes.


Shortage aheadA product on the standing order will run short. A replacement that does the same job in the kitchen's dishes.


FillA few more units make a full case.




Code finds the candidates from order history, stock and dates. A model only picks among them and writes the reason, and a reason that states a number the candidate does not contain is thrown away. Every proposal is judged by the rule engine against the buyer's mandate before it leaves (rules V1 to V7 below), and a proposal a rule refuses is never sent. The customer's agent reads proposals with list_proposals and answers with answer_proposal. Accepting gives a normal checkout. The buyer's mandate says which kinds its agent may accept alone and how much extra spend a week. Valio Aimo can switch proposals off per customer.



When there is not enough for everyone


On a Monday morning every kitchen's agent asks at the same second. First come, first served would give the whole stock to whichever agent is fastest. Rule L1 stops that.


When the stock of a product for a day is under the demand expected from order history, the product goes on allocation. Each customer can take its contract share: its usual order of that product against the short stock, the same fraction for everyone. Hospital, school and elderly care kitchens are guaranteed at least 60% of their usual order first. An agent that asks for more gets a signed offer for its share, with the reason in plain words under wholesale.allocation and the ways out: a listed substitute for the rest, the rest later ("rest": "later", a waiting list), or the share alone. Shares nobody claims are released to the customers still waiting, again by share.


An agent is told only its own numbers, such as "46 of your 80 litres". Total stock and other customers' orders stay with Valio Aimo. The control room replays the last recorded rush: 60 kitchens' agents on different models and one short product. The measured result is at /api/rush/latest.



The signed offer


A checkout is the offer. Valio Aimo signs the whole document: lines, prices, VAT, delivery date, order cut-off, the hold, and the outcome of every rule. Status tells the agent what to do next.




ready_for_completeInside the agent's authority. It may sign and order.


requires_escalationA person must decide. continue_url is the approval link.


incompleteCannot be ordered as asked. The messages say why and offer alternatives.


completedOrdered. The order is attached.


canceledDropped or rejected. Stock released.




To order, the agent signs the offer's digest with the key from its mandate and sends that as ap2.checkout_mandate. If the price or stock changed in between, the gateway refuses and issues a new offer instead of quietly ordering something else.



The rules

When something goes wrong


Errors are data the agent can act on. Each has a code, a plain sentence and, where it helps, alternatives.




insufficient_stockNot enough for that day. Says how much of the buyer's request can be supplied and lists substitutes.


cutoff_passedToo late to order that product for that day. Lists what can still arrive.


invalid_quantity_incrementThe product sells in fixed multiples.


product_not_foundUnknown product id.


approval_requiredA rule asks for a person. The checkout carries the link.


policy_deniedA rule refuses. No approval can change it.


product_recalled, short_at_warehouse, delivery_delayedThe product is blocked by a recall, or this account has an open problem with it. Settle the issue first.


offer_expired, offer_changedThe hold ran out, or price or stock moved. Update the checkout for a fresh offer.


mandate_required, mandate_expired, mandate_invalid_signatureNo valid mandate.


mandate_scope_mismatch, agent_missing_keyThe agent did not sign this exact offer with the key in its mandate.





After the order


Most trouble in wholesale comes after the order is placed. Valio Aimo can report three things on an order: the warehouse is short, the delivery is late, or a batch is recalled. Each report is a notice signed by Valio Aimo that lists the ways out the gateway worked out itself: take what there is and get the rest credited, fill the gap with a substitute that keeps the order's requirements, accept the new day, or cancel. Every way out says what it costs or credits and whether the agent may take it alone.


The agent picks one. A way out with new goods goes through the same signed offer, rules and approval link as any order and ends as a linked order. One without new goods becomes a signed amendment. The original confirmation is never edited, so it still checks out byte for byte.


A recall starts from the lot. Every order line gets a lot when the order is placed (the challenge data has none, so the gateway assigns them). One recall finds every order and customer that got the lot, tells all of their agents at once, and blocks the product for new orders until it is closed. Keeping recalled goods is not an option an agent or a person can pick.



Proof


Four signatures sit behind every order: the buyer's on the mandate, Valio Aimo's on the offer, the agent's on its acceptance, and Valio Aimo's on the confirmation. A fifth is added when a person approves. All are ES256 over canonical JSON (RFC 8785), so anyone with the public keys can check them. The order page does exactly that in your browser, and lets you change a price by one cent to watch the check fail. To take neither the page nor the keys from this server, run verify/verify_order.py from the public repository on an order's address: one file, no gateway code, Valio Aimo's key pinned in the repository.


The approver's own device. An account enrols a phone or laptop as its approver. On a device with a fingerprint, face or screen lock the key is a WebAuthn passkey; in a browser without one it is a key the browser makes and keeps, and the record says which of the two signed. Either way the key is made on the device and never leaves it; the gateway keeps only the public half. What the device signs is the decision itself: which checkout, its digest, approved or rejected, by whom, the note, and each product and allergen the approver ticked. So the signature cannot be moved to another order, turned from a no into a yes or stretched to a line nobody looked at, and nobody else can produce it: not the agent, not Valio Aimo, not this server. What it does not prove is who holds the device. The first time an account needs a person, the approval link makes the device it is opened on that account's approver, and the approver types their name. The asker's own browser is refused, but a second browser of the asker's own would pass as the first approver. In production enrolling a device sits behind the approver's own Minun Aimo sign-in and role, which this prototype does not have. From then on the link alone neither approves nor enrols: an approval without the device's signature is refused, and saying no still needs only the link. The order page checks the device signature again in your browser, from the record alone. Enrolling is the buyer's act: from the account's own session, or through a 15-minute link the account made. Try it on the demo page under “The approver's device”.


What the data does not say. 4,233 of the 13,546 food products in the challenge data (31%) carry no allergen declaration at all, among them salmon fillets, shelled almonds and Dijon mustard. Rule A1 never passes such a product on an exclusion. It names the line, a person decides, and the account remembers the clearance per product and allergen. Where the product's own name points at the excluded allergen, a blank is not something a person can clear: the salmon fillet is refused for a kitchen that excludes fish. The numbers are on the proof page.


Every step is also written to a ledger where each link is over the digest of its entry body: digest = sha256(canonical_json(entry_body)); hash = sha256(previous_hash + digest). Readers can verify withheld entries without seeing their confidential body. See /ledger.


The gateway can also write the hash at the head of the ledger into a memo transaction on Solana devnet every few minutes, so not even the operator could rewrite history behind an anchor without it showing. Only the hash leaves the gateway. State: /api/anchor.

What is real here and what is not




RealLive calls to the challenge's price and availability API for every offer. The challenge's product data, delivery reliability and carbon figures. The signatures, the rules, the ledger. The agents: Claude, GPT, Gemini and open-weights Gemma models making their own tool calls. Approvals signed on the approver's own device, by a passkey or by a key the browser holds. Gemini reading the menu photo. Every number on the pages comes from a recorded run on this server and links to it.


Stand-inThe buyers, their order histories, their standing orders and the sandbox accounts are invented. The kitchen's recipe cards are ours, 27 of them. The sample menu photos were made with an image model and are labelled as samples; you can upload your own. Best-before dates for short-dated stock are assigned by the gateway, because the challenge data has none. On the demo accounts the buyer's signing key is kept by this server, so that a visitor can order without setting anything up. It does not have to be: a buyer can register its own key and sign its agents' mandates itself, and the order's record says which of the two happened. The approver's key is real: it is made on the phone or laptop that opens the approval link and never leaves it. Two cases are still approved by link with the gateway's own key on the record, and the record says so: the simulated customers on /tower, where a script plays the approver, and a browser that can neither make a passkey nor keep a key. Stock holds live in this gateway, not in the ERP. Orders stop here instead of going to order management.


EstimatedThe time to do the menu order by hand is 45 seconds a line, our assumption, until someone finishes /byhand. The page says which it is.


Not doneNo order has been sent through a real Peppol access point; the XML itself validates (see the standards table). No payment step: orders go on the customer's existing invoice terms, so no payment data passes through an agent.





From here to production


    

  1. The chat inside Minun Aimo. A few pilot kitchens, Valio Aimo's sign-in, each customer's own contract range and prices. The signed-in person confirms every order, and it enters the web shop's existing order flow.
    2. 

  2. Outside software, read only. For customers Valio Aimo chooses, their own purchasing software can look up and plan, not order. Nothing can go wrong with an order because there is none.
    3. 

  3. Re-orders with approval. Orders for products the customer already buys, each one approved by a person. Orders enter the webshop's existing order flow, so credit checks, picking and invoicing stay as they are.
    4. 

  4. Mandates. Customers set limits in the webshop account settings. Orders inside them go through alone. The buyer's key comes from their company sign-in, which also gates who may enrol an approver's device; the approval link goes to email or Teams and is signed on that device.
    5. 

  5. Open ordering. New products and substitutes inside the mandate. Peppol orders out to customers who already use it.
    6. 



Rate limits are enforced in code: token buckets apply per agent key and per customer account, with a forwarded-IP bucket for unauthenticated traffic. The defaults are 60 request burst and 5 requests per second for an authenticated agent or account, and 60 burst and 4 requests per second per IP; limits are tunable with AIMO_AGENT_RATE, AIMO_ACCOUNT_RATE, AIMO_IP_RATE and their burst settings. A 429 includes retry_after. Catalogue harvesting without a checkout is refused under W4 and contributes to automatic suspension.
